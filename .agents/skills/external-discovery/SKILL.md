# External Discovery and Reuse

Activate before substantial new capabilities, subsystems, frameworks, algorithms, models, infrastructure, evaluation systems, difficult custom mechanisms, rewrites, repeated failures, unfamiliar domains, course corrections, or novelty claims. Routine fixes do not require exhaustive discovery.

Search the underlying problem, not only BPDC terminology. Use appropriate GitHub/GitLab projects, packages, papers, standards, APIs, SDKs, benchmarks, and adjacent technical work. Evaluate functional overlap, architecture/API fit, license and asset provenance, maintenance, security, tests, dependencies, determinism, performance, integration cost, and revalidation cost.

Classify material candidates as `ADOPT`, `WRAP`, `EXTEND`, `FORK`, `COMPOSE`, `REFERENCE`, `BENCHMARK`, `BUILD`, or `REJECT`. External discovery does not authorize replacing qualified work. If a discovery materially changes strategic direction, return it to the Architect.

Record material findings in `.agent/EXTERNAL.md` with source, freshness, overlap, disposition, rationale, qualified-work impact, and recheck trigger. A search is evidence about coverage under stated limits, not proof that no other solution exists.
